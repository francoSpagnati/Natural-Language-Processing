# Dipendenze del progetto, aggiunte man mano che gli step le richiedono.
# Ogni voce e' motivata: il progetto richiede di poter giustificare ogni scelta.
#
# Python >= 3.10 (sintassi `X | None` nelle annotazioni di tipo).
#
# --- Step 0: esplorazione dati ------------------------------------------------
# Nessuna dipendenza esterna. Il caricamento usa solo `json`, le sonde `re`, i
# test `unittest`: tutto libreria standard. Restare a zero dipendenze in questa
# fase e' voluto, cosi' l'esplorazione e' riproducibile ovunque senza installare
# nulla e senza che una versione di libreria possa alterare i risultati.
#
# --- Step 1: schema dello stato paziente -------------------------------------
# Pydantic valida i dati invece di limitarsi a descriverli, genera lo JSON
# Schema dei file intermedi, ed e' comunque richiesto dallo step 10 per il tool
# MCP: definire lo schema altrove significherebbe mantenerne due versioni.
pydantic>=2.0

# --- Step 3: pipeline A deterministica ---------------------------------------
# PhraseMatcher confronta token e non caratteri, quindi non trova "ictus" dentro
# "peri-ictus", e scala su ~10.000 forme dove un'alternanza di regex no. Il
# documento tokenizzato serve comunque alla logica di negazione, che ragiona su
# frasi e distanze in token.
#   Richiede anche il modello italiano:
#   python3 -m spacy download it_core_news_sm
spacy>=3.7

# --- Step 4: pipeline B (estrazione con LLM) ---------------------------------
# Nessuna dipendenza aggiunta. Le chiamate a Google AI Studio passano da
# `urllib` della libreria standard (vedi src/llm_backend.py): il protocollo e'
# una singola POST JSON, e tenerla esplicita mantiene visibile nel codice il
# formato del messaggio invece di nasconderlo dentro un SDK, senza legare la
# riproducibilita' dei risultati alla versione di un pacchetto.
#
# Serve invece una chiave API in `.env.local` (non versionato):
#   GEMINI_API_KEY=...
#
# --- Step 5: pipeline C (NER + entity linking) -------------------------------
# Il riconoscitore di entita' e' un transformer per classificazione di token,
# affinato sulle etichette silver prodotte dalla pipeline A. `transformers`
# fornisce il modello e il tokenizzatore veloce (serve la mappa di offset per
# allineare intervalli di caratteri e sottotoken); `torch` e' il motore di
# addestramento. Il ciclo di addestramento e' scritto a mano invece di usare
# `Trainer`: quaranta righe in cambio della visibilita' di ogni passaggio.
#   Modello di base: IVN-RIN/bioBIT (BERT italiano biomedico), scaricato
#   automaticamente al primo addestramento.
transformers>=4.40
torch>=2.0

# --- Step 7: knowledge graph RDF ---------------------------------------------
# Il grafo tiene tre descrizioni parziali dello stesso paziente con la
# provenienza di ciascuna, e le domande dello step 8 si pongono in SPARQL invece
# di essere ricalcolate in Python: se la risposta si ottiene interrogando, la
# struttura e' quella giusta. rdflib fornisce il grafo in memoria, il parser e il
# serializzatore Turtle e il motore SPARQL 1.1, e non richiede un triple store
# esterno, il che tiene il progetto eseguibile senza servizi da installare.
#   I vocabolari usati sono standard, non inventati: PROV-O (W3C Rec. 2013) per
#   la provenienza, SKOS (W3C Rec. 2009) per ATC e ICD-10, DCMI Metadata Terms
#   per citare le fonti. Sono tutti forniti da rdflib.namespace.
rdflib>=7.0

# --- Step 10: il server MCP --------------------------------------------------
# SDK ufficiale del Model Context Protocol. Serve sia al server (`MCPServer`,
# che in mcp 1.x si chiamava FastMCP) sia al client locale (`ClientSession` e
# `stdio_client`), quindi una dipendenza sola copre le due meta' dello step.
#   Attenzione alla versione: da mcp 2.0 `from mcp.server.fastmcp import FastMCP`
#   non esiste piu' ed e' diventato `from mcp.server.mcpserver import MCPServer`.
#   Gran parte della documentazione in giro e' ancora ferma a 1.x.
mcp>=2.0

# Il client locale parla con ollama, che espone le chiamate a strumenti nel
# formato di OpenAI. La traduzione fra i due dialetti sta tutta in
# `_schema_per_ollama`, in un punto solo.
ollama>=0.4

# La figura del grafo di conoscenza (`kb_build.py --figura`): networkx per il
# grafo bipartito condizioni-classi, matplotlib per il PNG. Niente pyvis: una
# pagina HTML interattiva non si stampa nella relazione.
networkx>=3.0
matplotlib>=3.8
